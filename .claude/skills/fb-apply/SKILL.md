# fb-apply

## 목적
- 쌓인 피드백을 실제 skills/rules/hooks/docs 파일 변경으로 이어지게 한다.
- "일관성": 반복 피드백이 다음 세션부터 자동 적용된다.
- "맞춤형": 사용자별 패턴이 시스템에 누적된다.
- ⚠️ **모든 변경은 항목별로 반드시 사용자 확인 후 적용한다. 무단 수정 금지.**

## 호출 방식

| 호출 | 동작 |
|---|---|
| `/fb-apply --project` | 프로젝트 피드백 처리 (`{프로젝트 루트}/docs/feedback/*.md`) |
| `/fb-apply` | 전역/프로젝트 여부를 물어본 후 처리 |

미처리 피드백이 5개 이상 쌓이면 적용 권장 알림을 띄운다.

## 경로

| 범위 | 읽기 경로 | 적용 로그 |
|---|---|---|
| `--project` | `{프로젝트 루트}/docs/feedback/*.md` | `{프로젝트 루트}/docs/feedback/applied/log.md` |
| 전역 | `~/.claude/docs/feedback/*.md` | `~/.claude/docs/feedback/applied/log.md` |

## 범위 확인 흐름

`--project` 플래그가 없을 경우 반드시 물어본다:
```
어떤 피드백을 처리할까요?
[1] 이 프로젝트 피드백 (docs/feedback/)
[2] 전역 피드백 — 모든 프로젝트 (~/.claude/docs/feedback/)
```

## 워크플로우

### 1. 범위 결정
- `--project` → 프로젝트 경로
- 플래그 없음 → 위 질문으로 범위 선택

### 2. 미처리 피드백 수집
```
{경로}/*.md 읽기
"상태: [ ] 미처리" 항목만 추출
```

### 3. 카테고리별 그룹화 및 요약 출력
```
rule       → N개
skill      → N개
convention → N개
behavior   → N개
other      → N개
```

### 4. 변경 제안 생성

카테고리별 처리 대상:
- `rule` → 영향 대상 rule 파일에 추가/수정 내용 제안
- `skill` → 영향 대상 SKILL.md 수정 내용 제안
- `convention` → 해당 convention rule 파일 수정 제안
- `behavior` → `rules/02-behavioral-guardrails.md` 또는 응답 규칙 파일 수정 제안
- `other` → 사용자에게 처리 방향 직접 물어봄

제안 출력 형식:
```
## 변경 제안 #N
- 피드백: #{번호} — {원문 요약}
- 대상 파일: {파일 경로}
- 변경 내용:
  Before: {기존 내용 또는 없음}
  After:  {제안 내용}
- 적용 근거: {왜 이렇게 바꾸는지}
```

### 5. ⚠️ 항목별 사용자 확인 (필수, 건너뛸 수 없음)

각 변경 제안마다 **개별적으로** 확인을 받는다:
```
[변경 제안 #N] 위 변경을 적용할까요?
[Y] 적용   [N] 건너뜀   [E] 직접 수정 후 적용
```

모든 항목 검토 후 최종 요약:
```
총 {N}개 제안 중 {M}개 선택됨.
선택된 변경을 최종 적용하시겠습니까? [Y/N]
```

### 6. 적용 실행

최종 확인된 항목만:
1. 해당 파일 수정 (append 또는 targeted edit)
2. `{경로}/applied/log.md`에 이력 append:
   ```markdown
   ## YYYY-MM-DD 적용 이력
   - 피드백 #{번호}: {원문 요약} → {대상 파일} 수정
   ```
3. 원본 피드백 항목 상태 업데이트:
   `[ ] 미처리` → `[x] 적용됨 YYYY-MM-DD`

### 7. 완료 보고
```
✓ {M}개 피드백 적용 완료
  - 수정된 파일: {목록}
  - applied/log.md 갱신됨
```

## 게이트
- 미처리 피드백이 1개 이상 있다.

## 중단 조건
- 미처리 피드백이 없다 → "처리할 미처리 피드백이 없습니다."
- 모든 피드백의 영향 대상이 "미정"이다 → 각 항목에 대해 사용자에게 방향 직접 물어봄
